## 2. 背景与目标

### 2.1 背景

DSH（DeepSeek Harness）Web GUI 的右上角信息区目前仅显示 session_log 与余额信息。用户在长时间使用 DSH 进行重负载任务（长对话、批量推理等）时，希望随时掌握运行 DSH 的电脑的资源占用情况，以便判断是否需要调整任务规模或排查卡顿原因，而无需切换到任务管理器。

### 2.2 目标

在 Web GUI 右上角（session_log 与余额所在行的下一行）新增一行紧凑的性能信息，实时显示 DSH 所在电脑的 CPU 使用率与内存使用率。

### 2.3 成功指标

- 性能信息行正常显示且每 5 秒自动刷新；
- 显示的数值与系统任务管理器读数基本一致（偏差 ≤ ±2%）；
- 插件对 DSH 服务端与浏览器端的性能开销可忽略（CPU 采集进程占用 < 0.5%）。

## 3. 用户与角色

| 角色 | 说明 |
| --- | --- |
| 目标用户 | 所有使用 DSH Web GUI 的用户（单用户本机使用场景为主） |
| 使用场景 | 打开 GUI 即可在右上角查看性能；无需任何操作，数据自动刷新 |
| 角色与权限 | 无独立角色区分；插件为全局展示，不涉及用户操作与权限控制 |

## 4. 范围

### 4.1 In Scope

- 服务端（node 端）采集 DSH 所在电脑的 CPU 使用率与内存使用率；
- 服务端每 5 秒采集一次，并将数据推送到 Web 前端；
- 前端在右上角 session_log / 余额所在行的下一行以紧凑文字形式展示；
- 数据推送或采集失败时显示占位符 "--"，不中断其他功能。

### 4.2 Out of Scope（明确不做）

- GPU 使用率、温度、风扇转速等指标；
- 磁盘占用、网络上下行速率、进程列表；
- 指标可配置（开关、选择显示项）、自定义刷新频率；
- 历史曲线/图表、点击展开详情面板；
- 监控"浏览器所在电脑"（本需求明确监控 DSH 所在电脑）；
- 跨平台适配范围外的行为差异处理（见第 10 节开放问题）。

## 5. 功能需求

### FR-01 服务端性能数据采集

- **描述**：DSH 服务端（node 进程侧）按固定周期采集本机系统性能数据，采集项包括：CPU 使用率（百分比，0~100）、内存使用率（百分比）及内存已用/总量（字节或自动换算单位）。
- **优先级**：P0
- **验收标准**：
  1. 采集周期固定为 5 秒 ± 1 秒；
  2. CPU 使用率与系统任务管理器读数偏差 ≤ ±2%；
  3. 采集失败（如权限问题、API 不可用）时返回明确错误状态，不抛未捕获异常导致服务崩溃。

### FR-02 性能数据推送至前端

- **描述**：服务端将采集到的性能数据通过 DSH 插件事件机制实时推送到 Web 前端；推送内容包含：cpu（百分比数值）、memPercent（百分比数值）、memUsed、memTotal（容量数值）。
- **优先级**：P0
- **验收标准**：
  1. 前端在插件加载完成后能持续收到推送，无手动刷新页面也可自动更新；
  2. 推送数据为 JSON 结构，字段齐全，数值类型正确；
  3. 服务端未启动采集或出错时，前端收到明确的不可用状态。

### FR-03 右上角性能信息行展示

- **描述**：在 Web GUI 右上角信息区（session_log 与余额所在行的下一行）新增一行紧凑文字，固定格式：
  - CPU：`CPU 23%`
  - 内存：`MEM 58% · 8.2GB/16.0GB`（百分比取整；容量按 GB 显示，保留 1 位小数，总量不足 1GB 时按 MB 取整显示）
  - 整体示例：`CPU 23% · MEM 58% · 8.2GB/16.0GB`
- **优先级**：P0
- **验收标准**：
  1. 信息行位于 session_log 与余额所在行的下一行，左右对齐与上方行一致，不遮挡、不重叠任何现有元素；
  2. 每 5 秒随推送自动刷新，刷新时无闪烁、无布局跳动（行高固定）；
  3. 数据不可用时显示 `CPU -- · MEM --`，恢复后自动恢复正常显示；
  4. 页面刷新后信息行自动恢复显示（无需手动操作）。

### FR-04 插件安装与生命周期

- **描述**：插件遵循 DSH 标准插件规范（package.json 含 `dsh.client` 配置，web 平台注入），可正常加载、启用、停用；停用时信息行消失，重新启用后恢复。
- **优先级**：P1
- **验收标准**：
  1. 插件安装后 GUI 刷新即可生效，无需重启服务（若宿主机制要求重启，则说明文档中明确标注）；
  2. 停用插件后页面无残留 DOM 与报错。

## 6. 非功能需求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 性能 | 服务端采集开销：CPU 占用 < 0.5%，内存占用 < 20MB（假设）；采集与推送不影响 DSH 现有功能响应 |
| NFR-02 | 稳定性 | 采集失败、推送中断不得导致服务端崩溃或前端报错；前端连续运行 24 小时无泄漏性卡顿（假设） |
| NFR-03 | 兼容性 | 运行环境：Node.js（版本与 DSH 宿主一致，见第 9 节）；操作系统：Windows（用户当前环境），代码层面优先使用跨平台方案（假设） |
| NFR-04 | 可维护性 | 插件代码结构参照工作目录现有插件（如 dsh-approval-reminder）的 lib/ 分层：index.js（服务端）、client.js（前端注入）；附带 README 说明安装与配置方式 |
| NFR-05 | 可用性 | 信息行默认可见、无用户操作门槛；文本简洁，一屏内完整显示 |

## 7. 界面与交互

### 7.1 关键页面：GUI 右上角信息区

位置示意（新增行位于 session_log 与余额下方）：

```
┌──────────────────────────────────────────────┐
│  [会话日志] [余额]            (右上角信息区)  │ ← 现有行
│  CPU 23% · MEM 58% · 8.2/16GB               │ ← 新增行
└──────────────────────────────────────────────┘
```

### 7.2 交互

- 无点击、悬停等交互（首版为纯展示）；
- 刷新为自动进行，无手动刷新按钮。

## 8. 数据与接口

### 8.1 数据模型（推送载荷）

```json
{
  "cpu": 23,
  "memPercent": 58,
  "memUsed": 8800000000,
  "memTotal": 16000000000,
  "status": "ok"
}
```

- `status`：`ok` / `error`（error 时其余字段可为空，前端显示 `--`）。

### 8.2 外部依赖

- 服务端系统信息采集：优先使用 Node.js 内置能力（`os` 模块 + 两次采样差值计算 CPU 使用率）（假设）；如不可行，再引入轻量第三方库（如 `systeminformation`），具体以实现调研结论为准（写入开放问题）。

### 8.3 接口清单

| 接口/事件 | 方向 | 说明 |
| --- | --- | --- |
| `GET /api/dsh-system-monitor/stats` | 服务端 → 前端 | 前端每 5 秒轮询一次，载荷见 8.1；服务端后台每 5 秒采样缓存最新值 |

## 11. 验收与交付标准

1. ✅ 插件包（lib/index.js、lib/client.js、package.json、类型定义、README、docs）已交付到工作目录 `dsh-system-monitor/`；
2. ✅ 自动化测试通过：`node test/smoke.mjs`（路由与采集）与 `node test/client-sim.mjs`（前端注册与格式化）；
3. 安装到 profile 并注册后，GUI 右上角 session_log / 余额下方出现性能信息行，格式为 `CPU x% · MEM y% · a.bGB/c.dGB`；
4. 信息行每 5 秒自动刷新，数值与任务管理器偏差 ≤ ±2%（服务端实测一致）；
5. 移除插件注册后信息行消失且无报错、无残留（由 slots 生命周期保证）；
6. 连续运行 2 小时无崩溃、无内存持续增长异常（待实机观察确认）。
